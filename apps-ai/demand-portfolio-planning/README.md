# Demand-Portfolio Planning Agent

An agentic, human-in-the-loop demo for **demand, portfolio and project planning**.
A business demand flows through a two-act funnel — intake → pre-check → assessment →
board decision → portfolio fit → resource match → timeline & prioritization → project
planning handoff — with a person deciding at every gate. No demand is ever
auto-approved or auto-rejected.

Built on **Microsoft Agent Framework** workflows + **Foundry** models (no Agent
Service) + a FastAPI/SSE backend + a React (Vite) UI. Bilingual **de/en**, German by
default.

## What it demonstrates

The customer's real bottleneck is *after* the board — resource allocation, timeline,
and portfolio sequencing ("70 ideas, 3 people — in which order?"). So the demo reaches
all the way into **mini-skill-management** (who can do what → match), **portfolio
transparency**, and **explainable prioritization**.

Its defining trait is a **trust contract** made tangible: every fact the agent surfaces
carries provenance — `fact`, `assumption`, `open_question`, `generated`, or `unknown` —
rendered as colour-coded pills. The agent never invents business facts (missing fields
stay `unknown` and are raised at the pre-check gate), keeps confirmed facts separate from
assumptions and open questions, and never silently merges conflicts.

Three human gates use the Agent Framework `request_info` primitive to suspend the
workflow until a decision is made:

1. **Pre-check** — a **PRINCE2 Agile (Foundation)** readiness check across six themes
   (business case, organization, scope/product, plans/timeline, risk, resources). The
   demand is only "ready" for the board when every theme is covered; the reviewer can
   proceed (with an explicit confirmation if not), supply missing info, or block.
2. **Board** — approve as project / already solved / reject.
3. **Handoff** — accept the plan / adjust before handing off.

A separate **portfolio roadmap** view (`Roadmap` tab) places every project on one
timeline: running projects use their real dates, while the proposed backlog and the new
demand are sequenced by the same explainable prioritization. The project-plan timeline
itself is a deterministic PRINCE2 stage cadence anchored on today, so the plan always
shows concrete indicative dates rather than "open".

## Architecture

```
React (Vite) UI            FastAPI + SSE backend                Agent Framework workflow
───────────────            ─────────────────────                ────────────────────────
pick demand ──── POST ───►  /runs                ┌───────────►  bootstrap → intake (LLM)
stage stream ◄── SSE ─────  /runs/{id}/events     │              → precheck (LLM)
                                                  │   🚪 request_info  precheck gate
decision ─────── POST ───►  /runs/{id}/respond    │              → assessment (LLM)
stage stream ◄── SSE ─────  /runs/{id}/events     │   🚪 request_info  board gate
                                                  │              → portfolio fit (LLM)
seed panels ◄─── GET ─────  /api/seed-data        │              → resource match (LLM)
roadmap     ◄─── GET ─────  /api/roadmap          │              → plan (LLM) + deterministic
                                                  │                 prioritization + timeline
                                                  │   🚪 request_info  handoff gate
                                                  └───────────►  ProjectPlanningHandoff
```

Each LLM step sits in its own superstep so live stage events stream to the UI. The
backend run registry resumes the same workflow across all three sequential gates.

Resource matching, portfolio fit, and the planning artifacts are generated by Foundry
agents constrained to the **seeded source systems** only. The backlog **prioritization**
is a deterministic, explainable score (`2·value + 1.5·urgency − 1·effort −
1·resource_contention`); the LLM only narrates it, it never invents the ranking.

## Seed data (mock systems of record)

Deterministic, synthetic, and free of customer/account names
(`backend/src/demand_portfolio_planning/sources.py`):

- ~18 portfolio projects (some with deliberately unknown resources/dates, to dramatize
  the limited portfolio transparency the customer flagged);
- a ~12-person resource pool with a skill matrix and current commitments (the SAP FI
  capability is intentionally scarce and over-committed — the bottleneck);
- three seeded demands; the **payroll** one mirrors the use case's worked example.

## Local run

You need `uv`, `pnpm`, and an `az login` against a tenant with the Foundry project.

1. Copy `.env.example` to `.env` and set `AZURE_AI_PROJECT_ENDPOINT` and
   `AZURE_FOUNDRY_MODEL` (e.g. `gpt-4.1-mini`).

2. Backend:

   ```bash
   cd demos/demand-portfolio-planning/backend
   uv sync
   uv run uvicorn demand_portfolio_planning.app:app --reload --port 8138
   ```

3. Frontend (another terminal):

   ```bash
   cd demos/demand-portfolio-planning/frontend
   pnpm install
   pnpm dev
   ```

   Open <http://localhost:5248>. The dev server proxies `/runs` and `/api` to
   `localhost:8138`.

## Validate

Backend lint, type-check, and tests:

```bash
cd demos/demand-portfolio-planning/backend
uv run ruff check .
uv run mypy
uv run python -m unittest discover -s tests -t .
```

The tests drive the workflow through all three gates with fake agents (no Foundry) and
cover the happy path, the block/reject/already-solved branches, provide-info field
merging, deterministic priority injection, and handler-boundary memoization.

Frontend type-check + build:

```bash
cd demos/demand-portfolio-planning/frontend
pnpm build
```

## GenAI observability

Every model call is traced. When `APPLICATIONINSIGHTS_CONNECTION_STRING` is set (injected
by Bicep on deploy), OTel GenAI spans export to the Foundry project's Application
Insights, with `gen_ai.agent.id` on stage spans for Foundry agent attribution. Locally it
is a no-op, so the app runs unchanged without it.

## Deploy

Deployed with `azd` + Azure DevOps. The deployed shape is a public React frontend
Container App behind **ACA Easy Auth**, an **internal-only** FastAPI backend Container
App, both pulling from the shared ACR and running in the shared ACA environment against
the existing Foundry project (the backend's managed identity holds the Foundry User role).

Azure DevOps pipeline
`azure-pipelines-demand-portfolio-planning.yml` (definition id `14`,
`mcaps-microsoft.azure-demos.demand-portfolio-planning`) validates (ruff, mypy, tests,
`pnpm build`, Bicep), deploys with `azd`, syncs the Easy Auth redirect URI, asserts the
backend ingress is internal-only, verifies both rollouts with `tools/verify-deploy.sh`,
registers the external agent for Foundry tracing, and upserts the demo dashboard registry.
Easy Auth app-registration values are stored as pipeline variables (`AAD_CLIENT_ID`,
`AAD_APP_OBJECT_ID`, secret `AAD_CLIENT_SECRET`). The live URL is published in the demo
dashboard.

## Out of scope

By design, to keep the demo focused:

- It does not replace portfolio, project, HR, or resource systems of record.
- In-memory mode is process-local; runs do not survive a backend restart.
- The portfolio, resource pool, and demands are seeded mock data, not live integrations.
